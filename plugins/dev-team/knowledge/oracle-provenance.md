# Oracle Provenance

## Purpose

Classifies each test's expected value by how that value was determined. The classification drives whether the test verifies *correctness* (the system matches an independent standard) or merely *stability* (the system matches its own prior output).

## Taxonomy

### SPEC-DERIVED

The expected value is traceable to an external specification, standard, or documented requirement. Examples:

- Expected output computed from a written requirement (`// per RFC 7231, §6.3.1`)
- Value cited in acceptance criteria or a user story
- Result mandated by a protocol or industry standard
- Expected value from a product specification document

### INDEPENDENT

The expected value was computed independently of the system under test. Examples:

- Result of a hand calculation (`// 42 = 6 * 7, manually verified`)
- Output of a reference implementation written separately
- Value from a trusted external data source (known test vectors, published test cases)

### CIRCULAR

The expected value was captured from the system's own current output — golden files, snapshots, or assertions that encode "what we produce today." There is no external justification that this output is correct.

Examples:

- Snapshot / golden file assertions (Jest `toMatchSnapshot()`, `.toMatchInlineSnapshot()`, approved-files frameworks, `verify()` calls in ApprovalTests)
- Assertions written by recording a baseline run (`received → expected` copy)
- Assertions that exactly echo what the system returned when first observed, with no independent derivation
- AI-generated assertions that reproduce observed output without verifying it against a specification

## Detection Heuristics

### Identifying CIRCULAR oracles

Look for these signals at the assertion call site:

| Language / Framework | Circular oracle pattern |
|---|---|
| Jest (JS/TS) | `expect(x).toMatchSnapshot()`, `expect(x).toMatchInlineSnapshot(...)` |
| Jest (JS/TS) | Snapshot files in `__snapshots__/` |
| Vitest | `expect(x).toMatchSnapshot()`, `expect(x).toMatchInlineSnapshot(...)` |
| C# / ApprovalTests | `Approvals.Verify(...)`, `ApprovalTests.Verify(...)` |
| C# / Snapshooter | `Snapshot.Match(...)` |
| Python / syrupy | `assert result == snapshot` |
| Any | Assertion comment says "baseline", "captured from prod", "recorded output" |
| Any | Test file in `__snapshots__/` or `snapshots/` subdirectory with no rationale comment |

### Identifying INDEPENDENT / SPEC-DERIVED oracles

Positive signals:

- A comment citing a spec section, issue number, RFC, or requirement ID near the assertion
- An inline formula or derivation comment (`// expected = base * rate = 100 * 0.07 = 7.0`)
- A reference to a separately written oracle function not based on the SUT
- A test named after a known algorithm or well-specified behavior

### When to flag AI-generated assertions as CIRCULAR

If the test was generated by an AI tool (comment, commit message, or file header says so) and the expected values match what the system produced with no additional derivation, classify as CIRCULAR — the AI captured the current output, not a verified specification.

## Suite-level Ratio and Quality Cap

Count the oracle class for each assertion in scope:

```
circular_ratio = circular_count / total_assertions
```

| Circular ratio | Effect on finding |
|---|---|
| < 20 % | Note at suggestion level — consider adding provenance comments |
| 20 – 50 % | Warning — suite has meaningful circular-oracle contamination |
| > 50 % | Error — suite is circular-oracle-dominated; Test Quality contribution for the affected file is capped at 60 (out of 100) |

A circular-oracle-dominated suite verifies stability, not correctness. A system can regress silently and all snapshots will still pass after update.

## Coordination with test-smell-review

`test-smell-review` already flags snapshot tests as a named smell ("Snapshot Overuse"). When both agents run together:

- `test-smell-review` owns the *smell* signal (overuse, brittleness of snapshots).
- `test-review` owns the *oracle-provenance* signal (correctness vs. stability, quality cap).

Do not double-report the same snapshot assertion. If `test-smell-review` is running in the same session, `test-review` should note the oracle-provenance ratio in the summary without re-listing each individual snapshot as a separate finding.

## Relationship to Farley Score

The Farley Score's "Necessary" property — tests that fail only when real bugs exist — correlates with SPEC-DERIVED and INDEPENDENT oracles. A circular oracle can remain green after introducing a regression if the snapshot is updated. When the oracle-provenance ratio is available, it may inform "Necessary" scoring.
